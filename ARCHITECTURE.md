# Architecture document

## Actors folder

It contains actors like hero, ennemis or characters. They can be controlled
by players but they can also be controlled by the game itself.

- **Actor** is located at the root of `actors/` folder
- sub-classes of it are arranged in sub-folders

## Assets folder

It contains assets like Audios, Fonts or Images which are actually used in the game.

## Components folder

It contains reusable components which can be added to any scene to give them abilities.

### Components/Clickable

Add the `Clickable` to an element to make it clickable, it will need a `Area2D` as child to define the clickable area.

### Components/Collector (and Collactable)

To be used when players can collect items by pressing "action_collect" when they are close to it.

### Components/Magnet (and Magnetable)

Add the `Magnet` component to an element to attract elements which contain a `Magnetable` component.
The `Magnetable` component can only be used on `RigidBody2D` and its sub-classes.

### Components/Touch Controls

Add `TouchControls.tscn` to a scene to make it playable on a tablet: floating joystick (left half), jump and interact buttons,
camera drag on the rest of the screen. It presses the existing input actions, so game code does not change.
It frees itself on devices without a touch screen.

- `show_jump`, `show_interact`: hide the buttons the scene does not need (eg: CandyBucket only needs the joystick);
- `show_combat`: shows attack, switch tool and journal buttons (Chaseween);
- `force_visible`: shows it on desktop, for tests.

Game code reads actions (`action_attack`, `action_switch_tool`, `action_journal`...), never raw keys or mouse buttons,
otherwise the buttons cannot trigger them. Touches also emulate a mouse: ignore `InputEvent.DEVICE_ID_EMULATION` events when
a mouse click has a gameplay meaning.

### Components/Trigger (and Triggerrable)

To be used when elements can trigger other elements.

### Components/UI Controls

To be added on scenes containing buttons to play sounds on hover or on click.

## Resources folder

### Resources/Localization

One group of files for each part of the game. For instance, menus will use `MenuTranslations` files.

- `.xlsx` in the source of truth, the only one to be modified
- `.csv` is generated form the `xlsx` (in UTF-8)

### Resources/Theme

- `MenuTheme` is to be used for menus.

## Scenes folder

Contains scenes like levels and menus.

### Scenes/Console

The `GameConsole` is a UI for developers which allows to enter commands for debugging.
By default, on an AZERTY it opens when typing the "²" key or #.

To add it to a scene, add the `GameConsole` to it, and add `Command` children nodes.
Every `Command` nodes have to be configured to **target** an existing node of the scene,
onto an existing **function** with the right **parameters**.

To define a parameter there are 2 formats:
- `name:type` if parameter is mandatory (eg: `time:float`);
- `name:type:default` if parameter is optional, optionals must be last parameters (eg: `time:float:0.8`).

Allowed types are: `string`, `int` or `float`.

### Scenes/Minigames

#### Minigames/Labyrinth

`labyrinth/Labyrinth.tscn` is the base scene of every labyrinth (player, exit door, HUD, result overlay, timer).
Each labyrinth is an **inherited scene** of it (eg: `Level01.tscn`) which only adds walls, a floor and candies.
The time limit is not per labyrinth: it is shared by the whole run, see `Services/Labyrinth`.

To create a labyrinth:
- inherit from `Labyrinth.tscn`;
- set `extra_candies` (bonus candies won when the labyrinth is finished);
- set `next_level` (empty on the last labyrinth: finishing it goes back to `scenes/levels/main.tscn`);
- add `Candy` instances (`objects/candy_crystalberry.tscn` or `objects/candy_pumpkin.tscn`, both inherit `objects/candy.tscn`) under `Candies`: the total is the number of nodes in the `candy` group. Candies float 0.6 m above the floor (`y = 0.6`) and bob up and down (`bob_height`, `bob_speed`, random phase per candy). They are self-lit and each one has a small `OmniLight3D` in its own colour. Collecting a candy spawns a one-shot `objects/candy_sparkles.tscn` burst tinted with the candy's `sparkle_color`, and `Labyrinth` plays `assets/audio/collect.wav` (the candy is freed on pickup, so the sound lives in the labyrinth);
- keep corridors wide enough (~3 m) so the third-person camera does not clip into walls;
- walls use physics layer `Wall` (3), floors use `Floor` (2). The player starts at the origin facing -Z, the door is behind it (`z = 4` in the base scene, a level may move it).

`Level01` is a 6x6 cell maze built with `objects/wall.tscn` (the `assets/walls/wall.gltf` model, stretched to 5 m, with a collision box).
Corridors are 4 m wide (the width of `wall.gltf`) and walls are 1 m thick, so cells are 5 m apart: the maze is 30x30 m between wall centres.
The start cell is at the origin and the door is mounted on its south wall.

`Level02` is an 8x8 cell maze with the same rules (40x40 m between wall centres, start cell in column 4 of the bottom row, door on its south wall), 9 candies and 8 extra candies.
`Level01` points to it with `next_level`.

`Level03` is a 12x12 cell maze with the same rules (60x60 m between wall centres, start cell in column 6 of the bottom row, door on its south wall), 12 candies (all at dead ends) and 12 extra candies.
It is the last labyrinth: `Level02` points to it with `next_level`, and `Level03` has none.

#### Minigames/FactionTerritory

`faction_territory/FactionTerritory.tscn` is a solo fight against the computer: 5 sites on a line (x = -20 to 20), the player owns the first one, the enemy owns the others.
The goal is to collect candies (a score only, there is no win or loss). Decisions are in `docs/decisions/2026-10-23-faction-territory-minigame.md`.

- `Site`: a flag which belongs to a `Faction.Side`. `flip_to(side)` changes its owner and emits `owner_changed`. Sites are in the `sites` group. `capture_wait_time` (seconds, set per site in the Inspector) is how long every player unit waits at this site when it reaches it, whether the site is already owned or not. Enemy units do not wait.
- `Unit`: marches along the line, stops to attack the nearest enemy in range, and flips an enemy site it reaches when no enemy unit is standing near it. It uses distance checks on the x axis, not physics. Units are in the `units` group.
- `UnitStats` (Resource): health, damage, range, speed and `cooldown`. One `.tres` per type in `units/` (`rogue`, `ranger`, `mage`). The cooldown is the only cost of a unit.
- `UnitSpawner`: one per faction, with one cooldown per unit type. It spawns at the most-forward site owned by its faction, or at the rearmost one when `spawn_at_rearmost_site` is on (the player's spawner), or at `home_x` if it owns none.
- `EnemyAI`: every `spawn_interval` seconds, asks the enemy spawner for a random unit type which is not on cooldown.
- `FactionTerritory`: gives 5 candies per owned site every 20s (`PayoutTimer`), ends the round after 180s (`RoundTimer`), calls `ProgressionService.complete_world(&"faction_territory", candies)`, pauses the game and shows `FactionTerritoryResultOverlay`. "Continue" goes to `scenes/levels/main.tscn` and sets the `faction_territory_return_to_door` meta, so the player reappears at `FactionTerritoryPortal` (church door).
- `FactionTerritoryHud`: candies, "+N" payout popup, owned sites, remaining time and one `UnitButton` per unit type (the button reads the remaining cooldown from the spawner).

To add a unit type: create a `UnitStats` `.tres` (the `.glb` needs the same bone map as `Knight.glb` to play the idle and run clips of `Unit.tscn`) and add it to `FactionTerritory.ALL_STATS`.

## Services folder

### Services/Save (and ProgressionService)

Autoloaded script to use to store and load progression of the player.
Make sure `ProgressionService.init()` is called while starting the game.

Use:
- `ProgressionService.data`: to get the current value of Progression
- `ProgressionService.save(progression: Progression)`: to save the given progression
- `ProgressionService.get_total_candy()`: to read the global CANDY score
- `ProgressionService.is_world_completed(world_id)`: to query a world state
- `ProgressionService.complete_world(world_id, candy_amount)`: to validate a
  snake_case world id once, add its CANDY, and save both changes
- `ProgressionService.start_new_game()`: to reset progression for a new run
- `ProgressionService.get_completed_world_count()`: to read completed worlds
- `ProgressionService.get_available_world_count()`: to read the run world total
- `ProgressionService.are_all_worlds_completed()`: to test final completion

World identifiers available in the current run are listed in
`ProgressionService.AVAILABLE_WORLD_IDS`. Add a future world's snake_case id to
that list before calling `complete_world(...)`. When every id is completed, the
finale becomes available through the church door in the lobby and remains
consultable without changing the score. The optional player name is stored in
the same progression save and survives a new run.

To change the values to save you'll have to change:
- `ProgressionService._serialize()` method which serializes the progression object
- `ProgressionService._parse()` method which parses the saved value
- `Progression` class which is the structured data

### Services/Save (GraphicsSettingsService)

Autoloaded script which stores the graphics settings (`user://saves/graphics.json`) and loads them by itself in `_ready()`.

- `GraphicsSettingsService.data.particles`: are particles enabled (default `true`)
- `GraphicsSettingsService.set_particles_enabled(enabled)`: saves the value and applies it right away

When particles are disabled, every `GPUParticles2D/3D` and `CPUParticles2D/3D` of the game is hidden
(`visible = false`), including the ones added later at runtime. Nothing has to be done on a particles node.

### Services/Transition (and SceneTransition)

Use `SceneTransition.change_scene(...)` instead of good old `get_tree().change_scene_to_file(...)` to:
- add a fading transition between scenes;
- display the shared loading screen while the destination is prepared;
- load the destination asynchronously and expose real resource progress when available;
- execute an optional callback on a fully black screen, for saving purpose for instance.

When Godot cannot measure progress, `LoadingScreen` uses an indeterminate bar instead
of inventing a percentage. A failed load keeps the current scene, displays an error,
then reveals that last valid scene again.

`SceneTransition.run_fade(at_black, on_reveal)` applies the same protected black
fade to a UI state change within the current scene. Only one transition can run
at a time. The fade-out and fade-in durations are both configured to 0.35 s in
`SceneTransition.tscn`.
